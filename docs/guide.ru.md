# 1. Что такое PocketBucket и как читать это руководство

PocketBucket — открытый мобильный клиент для собственного сервера Atlassian Bitbucket Server / Data Center. Основная цель проекта — дать разработчику возможность просматривать pull request и в дальнейшем проводить код-ревью с телефона. Первая целевая версия сервера — Data Center 8.19.26. Это не клиент Bitbucket Cloud: облачный продукт Atlassian использует другой API и другие структуры данных.

Приложение обращается прямо к существующему Bitbucket по HTTPS. Собственного сервера PocketBucket, промежуточного прокси и отдельной учётной записи PocketBucket нет. Если корпоративный Bitbucket доступен только через VPN, пользователь заранее подключает штатный VPN устройства. Приложение использует уже доступную системную сеть.

Это руководство объясняет уже написанный код, причины решений и границы проверки. Оно не предполагает знания Kotlin или разработки мобильных приложений. Полезно понимать Git на уровне «репозиторий, ветка, коммит, pull request»; незнакомые термины разобраны в словаре.

## Что можно сделать сейчас

Работает последовательность: настроить подключение → увидеть доступные проекты → открыть репозитории проекта → увидеть открытые pull request репозитория → прочитать подробности конкретного PR. Можно обновить данные, загрузить следующую страницу, вернуться назад и удалить сохранённое подключение.

Это Milestone 1, то есть фундамент приложения. Просмотр diff, комментарии, approve, merge и decline ещё не реализованы. Установленное приложение не превращается в полноценную систему код-ревью только потому, что успешно собирается.

## Три разных уровня готовности

**Код реализован** означает, что соответствующий путь существует в исходниках. **Проверка выполнена** означает, что конкретный тест или сборка действительно запускались. **Готовность к эксплуатации** требует дополнительно проверить реальные устройства, политики авторизации сервера, системное доверие сертификатам и пользовательские сценарии. Эти уровни нельзя подменять друг другом.

## Чего в проекте пока нет

Нет просмотра изменённых строк кода, дерева файлов, истории коммитов, обсуждений, inline-комментариев, одобрения и отмены одобрения, слияния и отклонения PR. Нет push-уведомлений, нескольких аккаунтов, локальной базы для offline-работы и публикации в App Store или Google Play.

Это намеренное ограничение этапа. Если одновременно строить сеть, хранение, навигацию, diff и все операции записи, становится трудно понять, какая часть системы сломалась. Первый этап проверяет, что данные проходят весь путь от REST API до общего интерфейса на обеих платформах.

## Пример пользовательского пути

Пользователь открывает приложение и видит форму Connection. Вводит HTTPS-адрес с нужным контекстным путём, выбирает Username / password или Token и нажимает Connect. После успешной проверки секрет сохраняется средствами платформы. Затем приложение запрашивает первую страницу проектов.

Нажатие на проект открывает репозитории. Нажатие на репозиторий открывает его открытые PR. Строка PR показывает номер, заголовок, автора и направление веток. Экран подробностей добавляет описание, reviewers и сведения о репозиториях обеих веток. Кнопка Disconnect закрывает текущий HTTP-клиент и пытается удалить сохранённые credentials; ошибка удаления показывается явно.

# 3. Что вообще происходит в мобильном приложении

Исходники — это текст, который редактирует разработчик. Сборка превращает этот текст и зависимости в исполняемый продукт. У Android таким продуктом для разработки служит APK; у iOS Xcode собирает приложение `.app` для симулятора или устройства. Подписанный пакет для распространения — отдельный результат, который нельзя получить только переименованием файла.

После запуска операционная система создаёт процесс приложения. В нём работают UI, обработчики действий, задачи ожидания сети и объекты состояния. Процесс может быть остановлен системой. Поэтому данные в оперативной памяти и данные в постоянном хранилище имеют разный срок жизни.

## Экран, сеть и хранилище — разные обязанности

Экран показывает информацию и принимает действия пользователя. Сетевой код формирует HTTP-запрос и разбирает ответ. Хранилище отвечает за сохранение секрета между запусками. Если поместить всё в обработчик одной кнопки, такую кнопку трудно тестировать, а смена API начинает ломать интерфейс.

В PocketBucket действия координирует ViewModel. Она публикует состояние экрана, но не рисует кнопки и не выполняет шифрование самостоятельно. HTTP-клиент не знает о цветах, навигации или тексте кнопок. Платформенное хранилище не знает, какой проект сейчас открыт.

## Почему нельзя блокировать главный поток

Главный поток обрабатывает ввод и обновление интерфейса. Если на нём синхронно ждать медленную сеть или дисковую операцию, экран перестаёт отвечать. В проекте сетевые функции приостанавливаются через coroutines, а платформенное хранилище явно выполняет работу на фоновом dispatcher.

Слово `suspend` само по себе не означает «создать новый поток». Оно означает, что функция может приостановить выполнение coroutine. Выбор потока или пула потоков зависит от используемых API и dispatcher. Это различие особенно важно, когда добавляется новый файловый или системный вызов.

## Что сохраняется между запусками

Credentials сохраняются через защищённое хранилище. Текущий список проектов, открытая страница PR и положение навигации постоянно не сохраняются. При запуске приложение пытается восстановить сохранённое подключение и повторно проверить его. Это не cookie-сессия браузера и не бесконечная серия попыток входа.

# 4. Для чего нужны Kotlin Multiplatform и Compose

Kotlin — язык программирования. Kotlin Multiplatform, сокращённо KMP, позволяет часть Kotlin-кода использовать на нескольких платформах. Compose Multiplatform — библиотека для описания интерфейса, который также можно разделить между платформами. Эти технологии решают разные задачи: общий язык и бизнес-логика не требуют автоматически общего UI, но здесь выбраны оба подхода.

| Инструмент | Задача в PocketBucket |
| --- | --- |
| Kotlin Multiplatform | Общие модели, сеть, состояние, тесты и платформенные варианты |
| Compose Multiplatform | Общие экраны и компоненты интерфейса |
| Kotlin/Native | Компиляция Kotlin-кода для Apple-платформ |
| Gradle Kotlin DSL | Описание задач сборки в `.gradle.kts` |
| Ktor Client | HTTP-запросы с подходящим платформенным engine |
| kotlinx.serialization | Преобразование JSON в типизированные DTO |
| Coroutines и StateFlow | Асинхронные задачи и наблюдаемое состояние |
| Lifecycle ViewModel | Владение состоянием и задачами экрана |

## Какой код получается для iOS

iOS-приложение не запускает JVM. Kotlin/Native компилирует общий и iOS-специфичный Kotlin-код в нативный framework. Маленький SwiftUI-host в Xcode подключает этот framework и встраивает Compose через `UIViewController`.

Compose UI при этом не превращается автоматически в набор SwiftUI-кнопок и UIKit-списков. Интерфейс описан общими Compose-компонентами и работает внутри нативного приложения. Поэтому iOS-ощущения, жесты, доступность, клавиатура и поведение на устройствах требуют отдельного внимания.

JDK нужен Gradle и другим инструментам на машине разработчика и в CI. Из этого не следует, что Java необходимо устанавливать на iPhone. Для Android часть кода исполняется в среде Android Runtime; это тоже не обычная настольная JVM, которую пользователь ставит отдельно.

## Почему это разумный выбор здесь

Проекту нужны одинаковые REST-контракты, правила авторизации и логика экранов на двух платформах. Общий код уменьшает вероятность, что iOS и Android по-разному трактуют один ответ сервера. Цена — необходимость согласовать Kotlin, Compose, Gradle, Android Gradle Plugin и Xcode и всё равно проверять обе платформы.

Выбраны закреплённые стабильные версии: Kotlin 2.1.21, Compose 1.8.2, Ktor 3.1.3, coroutines 1.10.2, serialization 1.8.1, Lifecycle 2.9.1, AGP 8.9.2, Gradle 8.11.1. Это проверяемая комбинация, а не обещание всегда использовать самые новые релизы.

## Что означает commonMain

`commonMain` — исходники, общие для целевых платформ. `androidMain` и `iosMain` содержат код, который зависит от конкретной операционной системы. `commonTest` содержит общие тесты, которые можно выполнить в JVM-варианте или нативном варианте на Apple-платформе.

У `core` есть JVM-вариант для тестов на обычной машине и использования Android-приложением. На macOS регистрируются также iOS-цели. В `composeApp` Android — приложение, а iOS — framework. На Linux Apple-цели намеренно не регистрируются: наличие Gradle не заменяет Xcode и Apple SDK.

## Направление зависимостей

UI использует доменные модели и интерфейс `BitbucketRepository`. Он не разбирает JSON и не читает поля Ktor response. REST-адаптер реализует этот интерфейс и преобразует DTO в модели приложения. Платформа создаёт конкретное хранилище и подходящий HTTP engine.

Koin не добавлен: несколько зависимостей передаются через конструкторы и небольшую фабрику сессии. Это называется ручным внедрением зависимостей. Интерфейс repository здесь полезен как настоящая граница и точка подмены в тестах. Дополнительные use case классы, которые просто переадресуют один вызов, пока не нужны.

Возможность desktop означает, что будущий host сможет использовать JVM-вариант `core` и предоставить свои сетевой engine и хранилище. Готового desktop-приложения в репозитории нет.

# 6. Kotlin: необходимый минимум на примерах проекта

Код Kotlin читается легче, если сначала понимать несколько конструкций. Здесь объясняется только то, что реально встречается в PocketBucket; это не полный учебник языка.

```kotlin
val title: String = "Orbital Tools"
var loading: Boolean = false
val description: String? = null
```

`val` запрещает переприсвоить переменной новое значение; `var` разрешает. Но `val` сам по себе не делает вложенный объект неизменяемым. Тип `String` обозначает строку, `Boolean` — true/false, а `String?` допускает ещё и `null`, то есть отсутствие значения. Kotlin часто выводит тип сам, поэтому явное `: String` можно не писать.

## Модели и копирование состояния

```kotlin
data class Project(
    val key: String,
    val name: String,
    val description: String?,
)
```

`data class` создаёт удобные методы сравнения, копирования и текстового представления. Для обычных моделей это полезно. Для credentials такая автоматизация опасна: сгенерированный `toString()` мог бы включить пароль. Поэтому секреты оформлены обычными классами со скрывающим данные `toString()`.

Состояние экрана обновляется через `copy`: создаётся новое значение с изменёнными полями. Это помогает понимать, какое состояние увидит UI. Изменение объекта на месте без публикации нового состояния было бы труднее отслеживать.

```kotlin
mutableState.update {
    it.copy(loading = false, error = null)
}
```

`it` — аргумент короткой лямбды. Лямбда — функция, которую передают как значение. Здесь она получает предыдущее состояние и возвращает следующее. Такая форма обновления также предотвращает потерю независимых изменений состояния при атомарном обновлении flow.

## Интерфейсы, sealed и when

`interface` задаёт договор: какие операции доступны. `RestBitbucketRepository` реализует этот договор через HTTP, а тестовая реализация возвращает заранее заданные результаты. Экрану не нужно знать, какой вариант ему передали.

`sealed interface Route` описывает ограниченный набор маршрутов: Connection, Projects, Repositories, PullRequests, Details. `when` выбирает поведение для конкретного маршрута. Если добавить новый вариант, компилятор помогает найти места, где его необходимо обработать.

`?.` означает «выполнить только если значение не null». `?:` выбирает запасное значение. Например, пустое описание PR заменяется понятным текстом. `!!` требует ненулевое значение и падает при нарушении; такую конструкцию нельзя бездумно добавлять для обхода ошибки компиляции.

`internal` ограничивает доступ модулем. `private` скрывает деталь внутри области видимости. DTO имеют `internal`, чтобы не становиться публичным договором между UI и сервером. `@Serializable` подключает сгенерированный разбор JSON; это не команда сохранения секрета на диск.

# 7. Состояние экрана, coroutines и отмена

`AppState` — снимок текущего состояния приложения: маршрут, флаги loading/restoring, ошибка, списки, подробности PR и курсор следующей страницы. `MutableStateFlow` находится внутри ViewModel; наружу публикуется только `StateFlow`, доступный для наблюдения.

Можно представить StateFlow как табло с последним состоянием. Это не база данных и не журнал всех действий пользователя. UI подписывается на это табло с учётом lifecycle и показывает актуальные значения.

## Как Compose использует состояние

Compose описывает интерфейс функциями с `@Composable`. При изменении состояния он пересчитывает необходимые части UI. Разработчик описывает «если есть ошибка — покажи сообщение», а не вручную ищет уже нарисованную надпись и заменяет её текст.

`remember` удерживает локальное значение между пересчётами в пределах жизни соответствующего элемента композиции. Оно не гарантирует сохранение после закрытия процесса. Поля пароля намеренно не используют `rememberSaveable`: секрет не должен попадать в автоматически сохраняемое UI-состояние.

## Почему задачи принадлежат ViewModel

`viewModelScope.launch` запускает coroutine, связанную с жизнью ViewModel. При её очистке задачи отменяются. Текущий сетевой запрос дополнительно отменяется при переходе на другой маршрут или отключении сессии.

`CancellationException` всегда передаётся дальше, а не превращается в «ошибку соединения». Иначе нормальный уход с экрана мог бы показать сетевую ошибку на следующем экране. Завершение работы с HTTP-клиентом также является частью владения ресурсом: кандидат закрывается при неуспешном подключении, активная сессия — при disconnect и очистке ViewModel.

## Предсказуемые переходы

При загрузке показывается индикатор. При успешном ответе публикуются данные. Пустой результат отличается от ошибки. Если обновление списка не удалось, уже показанные данные сохраняются вместе с сообщением об ошибке. Это полезнее, чем очищать экран при кратковременном обрыве сети.

Back возвращает к родительскому маршруту и загружает его первую страницу заново. Android также подключает системную кнопку/жест Back. У iOS сейчас есть явная кнопка Back; нативный интерактивный swipe-back пока не реализован.

# 8. Один Connect: от кнопки до проектов

```diagram
connection
```

1. Compose передаёт введённые строки в `PocketBucketViewModel.connect`.
2. `ServerUrl.parse` и `Credentials` проверяют формат без обращения к серверу.
3. Фабрика создаёт сессию: HTTP engine, `BitbucketApi` и `RestBitbucketRepository`.
4. Репозиторий выполняет маленький запрос персонального dashboard.
5. Только после успешной проверки credentials сохраняются через `CredentialStore`.
6. ViewModel переключает маршрут на Projects и запрашивает первую страницу.
7. Ответ JSON превращается в DTO, затем в доменные модели, затем в новый `AppState`.
8. Compose показывает проекты из состояния.

## Зачем проверять dashboard, если нужны проекты

Некоторые проекты на сервере могут быть доступны анонимно. Успешный ответ списка проектов не доказывал бы, что введённый пароль принят. Персональный dashboard требует пользователя, поэтому подходит для проверки именно авторизованного подключения. Запрашивается максимум один элемент, поскольку содержимое PR здесь вторично.

Даже после успешного входа запрос проектов может отдельно завершиться ошибкой. Проверка авторизации и чтение данных — разные операции. В таком случае сессия уже установлена, а Projects показывает ошибку и возможность повторить чтение.

## Сессия в этом приложении

`Session` объединяет repository и функцию закрытия его HTTP-клиента. Это локальный объект владения ресурсами, а не серверная cookie. Basic или Bearer передаётся с каждым запросом; браузерный логин не используется.

При старте `store.load()` может вернуть сохранённое подключение. Приложение проверяет его снова и не переписывает секрет просто из-за восстановления. Если хранилище недоступно или авторизация больше не действует, пользователь видит проблему и решает, повторить подключение или удалить сохранённые данные. Автоматического бесконечного retry нет.

# 9. REST API, DTO и модели приложения

REST API — договор о сетевых запросах и ответах. В данном этапе используются только GET-запросы чтения. Имя namespace `1.0` в пути API не означает версию установленного Bitbucket: сервер 8.19.26 по-прежнему предоставляет эти маршруты REST 1.0.

| Операция | Путь после корня/контекстного пути сервера | Параметры |
| --- | --- | --- |
| Проверить авторизацию | `/rest/api/1.0/dashboard/pull-requests` | `start=0`, `limit=1` |
| Получить проекты | `/rest/api/1.0/projects` | `start`, `limit=25` |
| Репозитории проекта | `/rest/api/1.0/projects/{projectKey}/repos` | `start`, `limit=25` |
| Открытые PR | `/rest/api/1.0/projects/{projectKey}/repos/{slug}/pull-requests` | `state=OPEN`, `start`, `limit=25` |
| Подробности PR | `/rest/api/1.0/projects/{projectKey}/repos/{slug}/pull-requests/{id}` | Без пагинации |

Если сервер установлен по адресу `https://code.example.org/bitbucket`, слово `bitbucket` должно сохраниться перед `/rest`. Идентификаторы добавляются отдельными кодированными сегментами: специальный символ внутри slug не должен неожиданно менять структуру URL.

## DTO — форма ответа сервера

JSON — текстовая запись объектов, списков, строк и чисел. DTO, то есть Data Transfer Object, описывает структуру этой записи на стороне клиента. Например, `PullRequestDto` содержит `fromRef`, `toRef` и `author.user`, потому что так организован ответ Data Center.

Доменные модели отражают удобные для приложения понятия: `PullRequest.from`, `PullRequest.to`, `Person`, `Reviewer`. Функции `toDomain()` преобразуют DTO в эти модели. Изменение серверного JSON тогда локализуется в адаптере, а не распространяется по каждому экрану.

Неизвестные поля JSON разрешены: сервер может добавлять информацию, которая этому этапу не нужна. Но необходимые идентификаторы и `isLastPage` нельзя молча выдумывать. Необязательные описание и reviewers имеют явные значения по умолчанию. Статусы PR и reviewers сохраняются строками, чтобы неизвестное будущее значение не ломало разбор.

## Граница подтверждённой совместимости

Контракт покрыт вымышленными fixtures и MockEngine. Прямой доступ к официальной версии документации Atlassian в текущей среде возвращал CONNECT 403; свежая независимая сверка всех полей с v819 не выполнена. Это открытая проверка перед выпуском. Ни моки, ни зелёный CI не заменяют разрешённый интеграционный тест на одноразовом Bitbucket 8.19.26. Корпоративный сервер для этой работы не использовался.

# 10. Пагинация, обновление и исправления списков

Сервер возвращает данные порциями. Одна страница Data Center — объект с `values`, `isLastPage` и, когда есть продолжение, `nextPageStart`. Сервер может уменьшить запрошенный limit или использовать смещения, которые не равны числу возвращённых записей.

```json
{
  "values": [{"key": "ORBIT", "name": "Orbital Tools"}],
  "isLastPage": false,
  "nextPageStart": 73
}
```

При таком ответе следующая страница запрашивается с `start=73`, даже если пришёл один проект, а запрошено было 25. Приложение не вычисляет следующий курсор как `start + 25` или `start + values.size`.

## Как ограничиваются память и сеть

После первой страницы ViewModel хранит её данные и следующий курсор. Новый запрос отправляется только после Load more. Списки накапливаются по явному действию пользователя, а не загружаются целиком в фоне. Это не жёсткий лимит на общую память: пользователь всё ещё может вручную загрузить много страниц.

`isLastPage=true` завершает список, даже если ответ также содержит лишний курсор. Если последняя страница не объявлена, но корректного продвигающегося курсора нет, ответ считается некорректным. Это защищает от зацикливания. Пустая промежуточная страница с допустимым следующим курсором сама по себе не означает конец.

## Дефект, найденный при ревью: повторяющиеся записи

Пагинация по смещению не является снимком базы на один момент времени. Между запросами кто-то может открыть новый PR или изменить порядок списка. Одна и та же запись тогда попадает на соседние страницы.

Compose-списки используют стабильные ключи, чтобы различать элементы. Дубли ключа могли вызвать ошибку при размещении UI. Исправление удаляет повторы по ключу проекта или ID репозитория/PR, сохраняя порядок первого появления. Новая информация из повторной строки не заменяет уже показанную запись; полное обновление получает свежую первую страницу. Регрессионный тест проверяет все три вида списка.

## Дефект, найденный при ревью: положение прокрутки

Один и тот же Compose callsite списка использовался для разных маршрутов. Состояние прокрутки могло сохраниться при открытии следующего экрана: PR открывался бы сразу у конца подробностей. Контент теперь имеет ключ маршрута. Смена маршрута создаёт новое локальное состояние списка, а Refresh на том же маршруте не пересоздаёт его только из-за обновления данных.

# 11. Basic, PAT, HTTPS и ошибки доступа

Basic Authentication передаёт заголовок `Authorization: Basic …`, где имя пользователя и пароль разделены двоеточием и закодированы Base64. Base64 — кодировка, не шифрование. Защиту при передаче обеспечивает HTTPS с проверкой сертификата.

Персональный токен передаётся как `Authorization: Bearer …`. Отдельный username для этого метода не нужен. Токен также является секретом: любой, кто получил действующий токен, потенциально может использовать предоставленные ему права.

```text
Basic:  UTF-8("username:password") -> Base64 -> Authorization
PAT:    token -> Authorization: Bearer <token>
Оба варианта: только через HTTPS с системной проверкой TLS.
```

## Права и политика сервера

Для текущего этапа нужны обычная авторизованная учётная запись и доступ на чтение соответствующих проектов и репозиториев. PAT должен быть пользовательским и иметь достаточное право чтения репозиториев. Токен не выдаёт доступ сверх прав пользователя. Административные и write-права этому этапу не требуются; для будущих review/merge действий права нужно будет описать заново.

Успешный вход через браузерный SSO не доказывает, что сервер разрешает REST Basic. При 401 приложение предлагает проверить credentials и уточнить политику Basic у администратора. При 403 сообщение направляет к разрешениям аккаунта, scope токена и политике авторизации.

## Что делает клиент для защиты запроса

Разрешён только HTTPS. URL с логином/паролем внутри, query и fragment отвергается. Автоматическое следование redirect отключено: секрет не должен отправиться на неожиданный адрес. Перенаправление на страницу SSO считается проблемой подключения к REST, а не успешной авторизацией.

Не подключены HTTP-логирование, cookie-login и автоматические бесконечные повторы. Android дополнительно отключает retryOnConnectionFailure у OkHttp; Darwin отключает хранение cookies, URL cache и credential storage системной сессии. Используется стандартная проверка сертификатов, без собственного trust manager и без «принимать любой сертификат».

Если сертификат корпоративного сервера не доверен устройству, правильный путь — одобренная организацией настройка системных trust roots и VPN. Приложение не устанавливает сертификаты и не управляет VPN самостоятельно.

# 12. Как хранятся секреты

Общий интерфейс `CredentialStore` содержит `load`, `save` и `clear`. Сам интерфейс ничего не шифрует; безопасность обеспечивают конкретные платформенные реализации. Вся запись подключения, включая адрес сервера и username, помещается в защищённый payload.

| iOS | Android |
| --- | --- |
| JSON подключения хранится как Keychain item | JSON шифруется AES-GCM |
| Доступность: WhenUnlockedThisDeviceOnly | AES-ключ создаётся в Android Keystore |
| Секрет доступен только на этом устройстве при разблокировке | Ключ не экспортируется через API приложения |
| Security API проверяется по кодам результата | В app-private preferences лежат ciphertext и IV |
| Нет fallback в обычные preferences | Нет fallback к незашифрованному JSON |

## iOS: системный Keychain

`IosCredentialStore` использует Security API: поиск, обновление, добавление и удаление item. Доступность `WhenUnlockedThisDeviceOnly` означает, что item предназначен для текущего устройства и доступен, пока устройство разблокировано. Это не обещание одинакового поведения при переустановке на всех версиях iOS: такие случаи проверяются отдельно.

Kotlin/Native работает с Objective-C и C API. Поэтому в реализации видны CFDictionary, указатели, retain/release и opt-in для interop. Это локализованная платформенная сложность; общий UI не должен самостоятельно управлять CF-объектами.

## Android: ключ отдельно от ciphertext

Keystore хранит ключ, а приложение сохраняет только зашифрованные bytes и случайный IV. AES-GCM также проверяет целостность: изменение ciphertext не должно тихо превратить его в другое корректное подключение. Новое сохранение использует новый IV. Результат дисковой записи `commit()` проверяется, чтобы ошибка записи не выглядела успехом.

Backup приложения отключён; дополнительные правила исключают данные из cloud backup и переноса устройства. Это уменьшает риск переноса ciphertext отдельно от недоступного Keystore key. Аппаратная защита ключа зависит от устройства: код не обещает обязательный StrongBox на каждом телефоне.

## Пределы защиты

Секрет нужен приложению в памяти во время запроса. Строки управляются runtime и могут оставаться в памяти до освобождения; идеального обнуления всех копий не обещается. Защищённое хранение не спасает от полностью скомпрометированного устройства и не отменяет отзыв токена на сервере.

Хранилища выполняют работу в фоне и сериализуют обращения mutex. Ошибки не приводят к сохранению в открытом виде. Однако unit-тест с подставным `CredentialStore` не доказывает работу Keychain или Keystore: реальные системные сценарии остаются отдельной проверкой.

# 13. Тесты: что проверено и зачем

Тест полезен, когда проверяет поведение и способен обнаружить правдоподобную ошибку. Процент строк сам по себе не говорит, правильно ли формируется Authorization или закрывается клиент после ошибки сохранения. Для этого проекта важнее покрыть договоры и переходы состояния, чем добиться формальных 100%.

| Уровень | Инструмент/подмена | Что проверяется |
| --- | --- | --- |
| Credentials и URL | kotlin.test | Формат Basic/Bearer, UTF-8, validation, скрытие секретов |
| Сеть | Ktor MockEngine | Реальные пути, query, headers и заданные ответы без внешней сети |
| DTO и mapping | JSON fixtures через клиент | Вложенные структуры, обязательные/необязательные поля, совместимость |
| Пагинация | Заданные последовательные ответы | Курсоры, конец списка, повреждённые страницы |
| Ошибки | Ответы 401/403/404/другие статусы, исключения | Тип ошибки, отсутствие утечек, отсутствие retries, cancellation |
| ViewModel | Тестовый repository/store и coroutines-test | Connect, restore, persistence, navigation, refresh, страницы и ошибки |
| Регрессии ревью | Пересекающиеся страницы | Уникальные строки для ключей Compose |
| Сборка | Android Gradle и Xcode | Совместимость кода, ресурсов и инструментов |

## Как работает MockEngine

Тест передаёт клиенту специальный engine. Он получает настоящий объект запроса Ktor, проверяет путь, параметры и заголовки, а затем возвращает вымышленный JSON. Поэтому можно проверить, что клиент отправил Basic, а не просто убедиться, что вспомогательная функция вернула ожидаемую строку.

Настоящий HTTP-запрос к Bitbucket не отправляется. Тест не требует VPN, аккаунта, пароля или корпоративного адреса. Но он доказывает поведение только на заданном контракте: если fixture описывает сервер неправильно, зелёный тест сам этого не обнаружит.

## Как проверяется асинхронное состояние

`coroutines-test` позволяет управлять очередью coroutine без ожидания настоящих секунд. Подставное хранилище учитывает, сколько раз вызывался save; repository может вернуть данные, ошибку или отложенный ответ. Так проверяется порядок «сначала авторизация, потом сохранение», сохранение старых данных при refresh failure и отмена устаревшей загрузки при навигации.

При ошибке авторизации credentials не должны сохраниться, а созданный клиент должен закрыться. При ошибке записи секрета нельзя перейти к якобы сохранённой рабочей сессии. При удалении соединения ошибка clear должна быть видимой. Эти сценарии важнее большого количества тестов простых getter.

## Что тесты пока не доказывают

Общие native-тесты исполняют общий Kotlin-код в Apple-среде. Они не превращаются автоматически в UI-тесты и не проверяют системный Keychain, если тест использует memory store. Нет инструментального теста жеста прокрутки; исправление ключа маршрута проверено ревью структуры Compose и компиляцией. Также отдельно нужны проверки минимальных ОС, заблокированного устройства, переустановки, корпоративных сертификатов и VPN.

Точные количества и итоговые результаты после этого ревью приведены в финальной сводке PDF и в отчётах соответствующего CI. Их нужно связывать с версией кода, а не навсегда считать неизменным числом.


Путь Xcode в примере должен соответствовать установленному приложению. Системный Xcode по умолчанию может быть новее; его совместимость с закреплённым Kotlin/Native нужно проверять отдельно. Нельзя считать, что любое обновление Xcode безопасно для старого compiler toolchain.

## Первый запуск на Apple Silicon

```sh
./gradlew :composeApp:linkDebugFrameworkIosSimulatorArm64
open iosApp/iosApp.xcodeproj
```

В Xcode выберите схему `iosApp`, установленный iPhone Simulator и нажмите Run. Build phase вызывает `:composeApp:embedAndSignAppleFrameworkForXcode`; ручная отдельная сборка framework полезна для диагностики, но не требуется перед каждым Run. CocoaPods в этом проекте не используется.

На Intel Mac нужен target `linkDebugFrameworkIosX64` и тесты `iosX64Test`. На Apple Silicon используется arm64-симулятор. `iosArm64` обозначает физическое устройство; совпадающее слово arm64 не делает бинарники устройства и симулятора взаимозаменяемыми.

```sh
./gradlew :core:iosSimulatorArm64Test \
  :composeApp:iosSimulatorArm64Test
```

## Физический iPhone

Выберите свою команду в Signing & Capabilities и при необходимости уникальный bundle identifier. Подключите устройство и настройте доверие/режим разработки по требованиям Xcode. Для доступа к корпоративному серверу используются существующие VPN и доверенные сертификаты устройства.

CI не создаёт готовый подписанный IPA для произвольного телефона. Профили, signing identity и публикация в App Store — отдельная работа. Реальные корпоративные credentials не нужны для unit-тестов и не должны появляться в source control.

| Симптом | Что проверить |

# 16. Запуск Android и ежедневные команды

Для Android нужен JDK 21, Android SDK platform 35, build-tools 35.0.0 и platform-tools. Минимальная поддерживаемая версия — Android 8.0 / API 26, target SDK — 35. Target SDK влияет на применяемые системой правила, а min SDK задаёт нижний порог установки.

```sh
sdkmanager "platforms;android-35" \
  "build-tools;35.0.0" "platform-tools"
./gradlew :core:jvmTest
./gradlew :composeApp:testDebugUnitTest
./gradlew :composeApp:lintDebug :composeApp:assembleDebug
```

Android Studio может установить SDK через графический SDK Manager. После открытия root-проекта дождитесь Gradle sync, выберите `composeApp` и устройство/эмулятор, затем Run. Не путайте Gradle-модуль приложения с его package name `dev.pocketbucket.app`.

```sh
adb install -r composeApp/build/outputs/apk/debug/composeApp-debug.apk
```

APK собирается с debug-подписью и предназначен для разработки. Production signing и публикация в Google Play не настроены. Подписывающие ключи нельзя добавлять в репозиторий.

## Как устроить первый день без доступа к Bitbucket

Начните с unit-тестов и чтения fictional fixtures. Они выполняются полностью локально. Затем соберите приложение и откройте Connection screen. Для реального прохождения сетевого сценария нужен разрешённый доступный Bitbucket; вымышленный адрес из placeholder не заработает. Не следует подключаться к корпоративному серверу только ради проверки сборки.

В данном задании реальные серверы не использовались. UI-preview показывает отдельную вымышленную карточку, а не полноценный демонстрационный offline-режим приложения. Такой режим можно добавить позже как явный инструмент разработки, если он понадобится.

## Что проверять перед своим PR

Запустите core tests, ViewModel tests, Android lint и debug build. После native/platform изменений нужна также сборка и тесты на macOS. Приложите точные выполненные команды и честно укажите платформы, которых не было под рукой. «Не удалось выполнить» лучше, чем неподтверждённое «всё работает».

# 17. Результаты ревью и оставшиеся риски

Ревью выполнено по всему диффу foundation относительно исходной ветки main: архитектура, auth/API/DTO, пагинация, состояние UI, secure storage, платформенные entry points, Gradle/Xcode, CI и документация. Дополнительные независимые проходы смотрели API/безопасность, UI/state и платформы/сборку.

| Находка | Риск | Исправление |
| --- | --- | --- |
| Повторы между страницами списка | Повторяющийся stable key мог привести к падению Compose-списка | Дедупликация по идентичности, тест для проектов/репозиториев/PR |
| Общая прокрутка для разных маршрутов | Новый экран мог открываться не с начала | Ключ маршрута вокруг общего контента; Refresh остаётся в том же route |

Это реальные исправленные дефекты уровня P2: заметные функциональные проблемы без обнаруженной утечки секрета или нарушения TLS. В проверенных auth/API и платформенных реализациях дополнительных подтверждённых блокирующих дефектов не найдено. Такая формулировка не означает математического доказательства отсутствия ошибок и не является независимым security-аудитом.

## Какие проверки остаются перед реальным использованием

Нужно свежо сверить официальный контракт v819 и провести разрешённый тест на одноразовом Bitbucket 8.19.26. Нужны системные тесты Keychain/Keystore: save/load/clear, locked-device, переустановка, потеря/инвалидация ключа, backup/transfer. Нужны реальные проверки VPN, цепочки сертификатов, iPhone/Android UI, клавиатуры, больших шрифтов и accessibility.

Минимальные заявленные ОС — iOS 15 и Android API 26 — должны проверяться отдельно от современных CI-сред. Симулятор может отличаться от физического устройства по security services, производительности и системным ограничениям.

## Решения, которые приняты осознанно

Нет backend: клиент общается с уже существующим Bitbucket напрямую. Нет Koin и лишних use case: текущему размеру хватает конструкторов и одного repository contract. Нет offline database: сначала проверяется живой read-only поток. Нет API-заглушек для merge/approve: неподдерживаемая операция не должна выглядеть реализованной.

Есть ограничения UX: Back перечитывает родительскую страницу, Markdown не рендерится, интерфейс пока англоязычный, polish под iOS отложен. Эти ограничения описаны как задачи развития, а не скрыты за заявлением «кроссплатформенность всё решает».

# 18. Как безопасно развивать проект

Начинать лучше с небольшого изменения, которое можно объяснить одним пользовательским сценарием. Например: добавить дополнительное поле на карточку PR или улучшить сообщение для конкретной ошибки. Сначала найдите уже существующий путь данных, затем меняйте только нужные слои.

## Пример: новое поле в подробностях PR

Если сервер уже возвращает поле, сначала проверьте его по официальной versioned документации и fictional fixture. Добавьте поле в DTO с корректной обязательностью, затем в domain model и mapping, затем в UI. Напишите тест, который разбирает JSON и проверяет результат модели. Если поле отсутствует на части поддерживаемых серверов, отдельно проверьте этот случай.

Не нужно переносить полный DTO в экран ради одного поля. Иначе UI начнёт зависеть от серверных имён и деталей версии. Но и создавать новый Gradle-модуль ради одной подписи не требуется.

## Пример: новая операция чтения

1. Уточните endpoint, query, схему, права и пагинацию по официальному API Data Center.
2. Определите полезную модель результата и метод repository.
3. Добавьте HTTP-вызов, DTO и mapping в data layer.
4. Проверьте путь/заголовки/ответ/ошибки через MockEngine.
5. Добавьте состояние и действие ViewModel, затем экран.
6. Запустите обе группы проверок и опишите ограничения.

Для операций записи, например approve или merge, этого примера недостаточно: понадобятся дополнительные права, оптимистическая конкуренция по PR version, явное отображение результата и обработка конфликтов. Поле `version` уже сохраняется в модели, но операции записи пока не реализованы.

## Последовательность дальнейших этапов

Milestone 2 добавляет полноценное чтение PR и diff. Для diff важны объём данных, позиционирование строк и производительность на телефоне. Milestone 3 добавляет комментарии, inline-дискуссии, approvals и review actions. Milestone 4 улучшает UX, accessibility, производительность и совместимость.

Не стоит смешивать все этапы в один огромный PR. Малый diff проще проверить, протестировать и откатить. Apache 2.0 LICENSE уже есть; README и CONTRIBUTING объясняют вход в проект. Клиент неофициальный, без аффилиации с Atlassian; analytics и telemetry по умолчанию отсутствуют.

## Частые вопросы

**Нужно ли писать всё два раза?** Большая часть логики и UI общая. Сеть низкого уровня, хранение и host остаются платформенными. Две платформы всё равно нужно проверять отдельно.

**Почему Kotlin, если основной телефон — iPhone?** Выбрана общая реализация для iOS и Android. Kotlin/Native создаёт нативный Apple framework, который подключается к Swift-host. Это архитектурный выбор, а не требование устанавливать Kotlin на телефон.

**Можно ли добавить Bitbucket Cloud заменой адреса?** Нет. Это другой продукт, API и схема авторизации/данных. Поддержка Cloud была бы отдельной задачей и сейчас не входит в проект.

**Можно ли убрать ошибку сертификата кнопкой «доверять всем»?** Нет. Это ослабило бы защиту credentials. Исправляется системное доверие и инфраструктура подключения.

**Почему клиент читает только OPEN PR?** Так ограничен текущий endpoint вызова. Изменение фильтров — будущая функция, а не невозможность API.

**Где посмотреть дифф?** В PR #1 на вкладке Files changed. Коммит указывает точную версию; Actions показывает проверки соответствующей версии. Не сравнивайте старую красную проверку с уже исправленным коммитом.
